# Contributing to EvoFab

Thanks for helping build EvoFab. This guide keeps requirements, implementation,
review, and lab context connected across Notion, Codex, and GitHub.

## Workflow

1. Start from a Notion task. Use the EvoFab Tasks database as the canonical
   source of truth for implementation work.
2. Confirm the task has a goal, scope, acceptance criteria, test plan, relevant
   links, and intended branch name before coding.
3. Create a branch from the latest `main` unless the work explicitly depends on
   another unmerged branch.
4. Do not push directly to `main`. Open a pull request for review.
5. Before opening a PR, fetch the latest `main` and rebase locally.

```bash
git fetch origin
git rebase origin/main
```

Use one branch per Notion task whenever possible. If a task grows into multiple
independent changes, split the task or open follow-up tasks before the PR gets
large.

## Branch Naming

Use the prefix that matches the change:

| Prefix                         | Use for                               |
| ------------------------------ | ------------------------------------- |
| `feature/<short-description>`  | New functionality                     |
| `fix/<short-description>`      | Bug fixes                             |
| `docs/<short-description>`     | Documentation only                    |
| `refactor/<short-description>` | Restructuring without behavior change |
| `chore/<short-description>`    | Tooling, dependencies, config         |

## Pull Requests

Every PR must include:

- What changed and why
- How to test it
- Considerations, tradeoffs, known limitations, or follow-up work
- Screenshots or recordings for UI changes
- A linked Notion task and GitHub issue, if one exists

Use the repository pull request template in `.github/pull_request_template.md`.

## Coding Standards

Self-check before requesting review:

- New files start with a short header comment stating the file name and purpose.
- New files follow the existing project structure. Do not create new top-level
  folders without discussing first.
- New functions and components include a concise JSDoc comment unless the
  function is trivial and self-evident.
- Similar logic is reused or extended instead of copied.
- Components and functions keep a single responsibility.
- Code is formatted with Prettier before committing.
- README or docs are updated when setup, environment variables, feature behavior,
  or project structure changes.
- Dead code, unused imports, and commented-out code are removed.
- Existing tests pass, and new tests are added where the project already has
  coverage for the touched behavior.

### Header Comment Format

TypeScript / TSX:

```ts
// FileName.ts
// One sentence describing this file's purpose and role in the project.
```

Python:

```python
# filename.py
# One sentence describing this file's purpose and role.
```

### Doc Comment Format

```ts
/**
 * One-sentence description of what this does.
 * @param paramName - What this parameter represents.
 * @returns What the function returns.
 */
```

For short helpers, an inline form is fine:

```ts
/** Merges class names, filtering out falsy values. */
export function cn(...classes: Array<string | undefined | null | false>) {
```

## Formatting

Formatting is handled by Prettier in `evofab-app`.

```bash
cd evofab-app
npm run format
```

To check formatting without modifying files:

```bash
npm run format:check
```

In VS Code, install the Prettier extension and enable Format on Save.

## Commit Messages

Use short, present-tense Conventional Commit messages:

| Prefix      | Use for                               |
| ----------- | ------------------------------------- |
| `feat:`     | New user-facing feature               |
| `fix:`      | Bug fix                               |
| `docs:`     | Documentation only                    |
| `refactor:` | Restructuring without behavior change |
| `chore:`    | Tooling, dependencies, build config   |

Examples:

- `feat: add curvature trend chart to results page`
- `fix: correct printer reconnect handling`
- `docs: document Codex workflow`

Avoid vague messages such as `updates`, `fixed stuff`, or `WIP`.

## Local Setup

Requirements:

- Node 22 and npm 10+
- Docker Desktop
- Supabase CLI
- Python 3.11 for robot/camera hardware work

```bash
cd evofab-app
nvm use
npm ci
cp .env.example .env.local
npx supabase start
npm run dev
```

Most day-to-day development should use `npm run dev`, which starts the app in
mock-first mode and avoids contacting physical lab hardware. Use
`npm run dev:hardware` only for supervised hardware work on the lab network.

## Files To Leave Alone

- `evofab-app/.env.local` - local secrets and machine-specific values
- `evofab-app/next-env.d.ts` - generated by Next.js
- `node_modules/`, `.next/`, `playwright-report/`, and `test-results/`
- Python `__pycache__/` directories
